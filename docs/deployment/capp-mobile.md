# CAPP Mobile Deployment (EAS Build/Submit)

This is the CAPP Phase 12 addendum to this directory's Phase 16 runbook. It
covers the customer mobile app (`../../../customer-app`) specifically — a
separate Expo/React Native project with its own build/release track,
independent of everything in `production-checklist.md`, which covers only
this Next.js backend. Read `../customer-app/architecture.md` first if you
haven't — this file assumes the CAPP architecture it describes.

**Nothing in this file has been runtime-verified**, for the same reason
stated in this directory's `README.md`: this project was authored with zero
outbound network access, so `eas build`/`eas submit` have never actually
been run against Expo's servers here, and no real Apple Developer / Google
Play account has ever been used. Treat every command below as
reviewed-but-unrun.

## Why this is a separate track from the backend deploy

The backend (this repo) and the mobile app (`customer-app`) release
independently:

- The backend redeploys on every merge to its production branch, same as
  any web app (see `production-checklist.md`).
- The mobile app only needs a new build/submission when its own code
  changes, or when `EXPO_PUBLIC_API_BASE_URL` needs to point at a new
  backend URL — a backend deploy that doesn't change its public API shape
  or URL requires no mobile action at all.
- App Store / Play Store review takes hours to days, unlike an instant web
  deploy — plan mobile releases on that timeline, not the backend's.

## 1. Backend prerequisites

Before building the mobile app for a real store submission, the backend it
points at must already satisfy:

- [ ] `CUSTOMER_AUTH_SECRET` set in production (see
      `production-checklist.md` step 3) — the mobile app cannot
      authenticate a single customer without it.
- [ ] `APP_URL` is the final production domain, not a placeholder — this
      becomes both `EXPO_PUBLIC_API_BASE_URL`'s origin (below) and the
      domain that must serve the deep-link verification files (step 3).
- [ ] Rate limiting (`middleware.ts`) covers the customer auth routes —
      already fixed in CAPP Phase 12 (`/api/v1/auth/**`), just noted here
      as a "this must already be true" precondition, not a new step.

## 2. Mobile environment configuration

`customer-app/eas.json`'s `build.production.env.EXPO_PUBLIC_API_BASE_URL`
must point at the real backend from step 1, e.g.
`https://app.example.com/api/v1` — **not** a `localhost`/LAN address (those
only work for local Expo Go development, see `customer-app/README.md`'s
"Why hand-authored" section).

- [ ] Update `eas.json`'s `build.production.env.EXPO_PUBLIC_API_BASE_URL`
      to the real backend URL.
- [ ] Set `EXPO_PUBLIC_TERMS_URL`/`EXPO_PUBLIC_PRIVACY_URL` (see
      `customer-app/.env.example` and `src/legal/legalLinks.ts`) to real,
      published pages — **required** for App Store/Play Console review,
      not optional polish. Both currently ship unset in this build.
- [ ] Decide where these `EXPO_PUBLIC_*` values live for the build — either
      committed into `eas.json`'s `env` block (fine; `EXPO_PUBLIC_*` vars
      are inlined into the JS bundle at build time and are not secret, see
      `.env.example`'s own header comment) or via EAS's own environment
      variable store (`eas env:create`), whichever this project's actual
      EAS account setup prefers.

## 3. Deep-link domain verification

`useDeepLinkRestaurant` (CAPP Phase 12) and `app.json`'s
`associatedDomains`/`intentFilters` are wired against a placeholder domain
(`app.example.com`) — see `customer-app/README.md`'s "What's deliberately
not wired yet" for what that means functionally. Before Universal
Links (iOS) / App Links (Android) verify on-device:

- [ ] Replace `app.example.com` in `customer-app/app.json`'s `scheme`,
      `ios.associatedDomains`, and `android.intentFilters` with the real
      production domain from step 1 (same value as `APP_URL`, minus the
      scheme).
- [ ] Serve `/.well-known/apple-app-site-association` from that domain
      (JSON, no file extension, `Content-Type: application/json`) —
      identifies this app to iOS by its Team ID + bundle identifier. Not
      generated by this codebase; must be authored once real Apple
      credentials (step 4) exist.
- [ ] Serve `/.well-known/assetlinks.json` from that domain — same idea for
      Android App Links, keyed by the app's SHA-256 signing certificate
      fingerprint (available from EAS's credential store after the first
      production build, or from Play Console).
- [ ] Until both files are live and correctly verified, `https://` deep
      links degrade to opening a browser instead of the app — this is a
      graceful degradation, not a crash, but it means QR codes/marketing
      links won't open the app until this step is done. The `capp://`
      custom scheme works immediately regardless (no domain verification
      needed for a custom scheme), so it's a viable interim fallback for
      testing.

## 4. Store credentials (one-time setup)

- [ ] Apple: an active Apple Developer Program membership, an App ID
      registered for this app's bundle identifier with Associated Domains
      capability enabled, and an App Store Connect record created for it.
- [ ] Google: an active Google Play Console developer account, and an
      app record created in Play Console (Play Console requires at least
      one manual upload before `eas submit` can automate subsequent ones).
- [ ] `eas.json`'s `submit.production` is deliberately empty in this repo —
      no credentials have ever been entered here. Populate it (or rely on
      EAS's interactive credential prompts / `eas credentials`) with real
      values at submission time; never commit real credentials into
      `eas.json`.

## 5. Build

```bash
cd customer-app
npm install                      # never run in this sandbox — see README.md
eas build --platform ios --profile production
eas build --platform android --profile production
```

- [ ] Confirm `app.json`'s `ios.buildNumber`/`android.versionCode` were
      bumped from the previous submitted build (both currently `"1"`/`1` —
      the first-ever values, correct only for an actual first submission).
- [ ] App icons/splash screens are still an open gap (see
      `customer-app/README.md`) — `app.json` omits them rather than
      pointing at placeholder binaries. A build without them will likely
      be rejected by store review for using default/missing iconography;
      real design assets need to land in this repo before this step, not
      after.

## 6. Submit

```bash
eas submit --platform ios --profile production
eas submit --platform android --profile production
```

- [ ] After Apple/Google review completes, verify the deep link from step 3
      actually opens the installed app on a real device (not just the
      Expo Go dev client) — this is the first point in the whole sequence
      where that can be confirmed end-to-end.

## Rollback

Store review timelines mean a mobile rollback is not instant like the
backend's (`rollback.md`). If a shipped build has a client-side bug:

- [ ] Submit a fixed build through steps 5-6 again — there is no server-side
      "revert" for an already-approved store binary.
- [ ] If the bug is backend-compatible-breaking (the shipped app calls an
      API shape the backend no longer serves), prefer fixing the backend to
      stay compatible with the last-shipped mobile build over trying to
      force an emergency mobile release — the backend redeploys in minutes,
      the mobile app in days at best.
